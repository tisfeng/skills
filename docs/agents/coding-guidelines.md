# 编码规范

本文统一规定跨语言代码质量、依赖与命令行工具，以及文档、配置和源码资产。构建与测试见
[`build-and-test.md`](build-and-test.md)。

## 跨语言代码质量

以下规则适用于手写的 Python、Shell 和其他源码。

### 组织与命名

- 修改保持最小、可读且与现有风格一致，不夹带无关重构。
- 按功能和明确职责组织代码；解析、I/O、编排和验证混杂时，在当前任务范围内提取同级文件或模块。
- 每个源码文件聚焦一个职责；出现多个独立职责或超过项目 lint 阈值时评估拆分。现有大文件不自动
  纳入当前任务范围。
- 名称应表达意图；除简单循环索引外避免无语义的单字母变量和缩写，避免不必要的全局可变状态。
- 文件、类型和标识符遵循对应工具及所在目录的既有约定；代码库已经采用 async/await 时优先沿用。

### 注释

- 为公开 API，以及职责、约束、副作用或实现原因不明显的模块、类型和函数添加必要文档；不注释
  明显 accessor 或薄 wrapper。
- 注释说明代码本身无法表达的意图、约束或副作用，并随行为更新；格式遵循项目工具配置和相邻
  代码风格。
- 保留现有文件头；新文件遵循相邻文件模板，不使用 Agent 名称作为作者。

## 依赖与命令行工具

- Python、Node 和 Shell 工具优先使用标准库或平台内置能力；新增依赖必须有明确收益。
- 命令行工具的失败信息应说明动作、目标和恢复方式，且不得静默覆盖用户文件。

## 文档、配置与源码资产

- 文档使用清晰术语和具体行为；避免脱离上下文的抽象限制。链接使用相对路径，重命名后更新活动
  引用而不篡改 completed plan/history 的历史事实。
- 修改 TOML、JSON、YAML 或 Markdown 时，同时验证格式、调用方和受影响文档；不把结构校验当作
  运行时或发布验证。
- `skills/` 的手写源码、脚本和测试保持职责内聚。第三方或生成内容只有在明确标识且具备来源时
  才可整体保留，不得伪装成项目手写实现。
- 修改发布的 Skill 时阅读其 `SKILL.md`。
