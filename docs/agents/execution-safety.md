# 执行安全与变更门禁

## 核心规则

- `planning` 只读取、搜索、诊断、起草和报告。
- implementation 必须有明确授权，并且只修改任务允许的路径。
- 保留用户既有 staged、unstaged 与 untracked 改动；不使用 reset、clean 或覆盖式操作清理现场。
- 变更前后执行与风险相称的验证；未运行的验证必须明确说明。
- implementation 产生仓库文件差异时，同步维护本任务的 history。

## 写入前检查

首次写入前记录 `initial_head`、初始 staged/unstaged/untracked 路径、冲突状态、任务允许路径，
以及与任务相关的分层 diff 或未跟踪内容摘要。随后确认：

1. 用户已授权当前类型的写入，目标和允许路径明确。
2. 初始 Git 状态可以区分用户内容与 Agent-owned paths。
3. 已确定必要的 active plan、history 和最终验证。
4. 已根据请求语义确定 `delivery_authorization`，且没有遗漏跨轮仍有效的限制。

这些条件由 Agent 根据真实状态判断，不要求用户逐项确认。关键授权、范围或产品决策不明确时，
暂停依赖它的写入并继续其他独立且已授权的工作。

## 执行流程

1. 按请求边界确定意图、交付授权和安全状态。
2. 在首次写入前冻结初始 Git 快照、允许范围和 Agent-owned paths。
3. 只实施获准路径，完成必要检查；产生仓库差异时同步维护 history。
4. 所有内容稳定后运行覆盖最终快照的验证，再交给 Git 工作流处理交付。
5. implementation 的自动本地提交不能扩大为 push、pull、rebase、merge 或发布。

## 保护状态

- 初始索引非空时保留暂存边界并跳过自动提交；显式 staged 交付仍按其授权处理。
- 用户改动与 Agent 路径无法安全分离、HEAD 或索引异常漂移、存在冲突时暂停对应交付。
- 必要验证失败时暂停提交，继续范围内诊断、修复和复验；不得把旧验证写成最终通过。
- 缺少 history 时在允许范围内补齐；用户明确排除该路径时不扩权，并报告自动交付受阻。
- 保护状态不撤销其他已授权的独立检查或修复，也不把 planning 升级为 implementation。
