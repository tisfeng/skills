# 代码维护

## 确定范围

先读项目规则，检查工作树并保护已有改动。用户要求清理或重构时，在授权范围内执行。
用户只要求检查、评估或方案时，仅读取和报告。

用户指定提交范围、目录或全仓时，以指定范围为准。否则，从当前 `HEAD` 可达的历史中
选取最近 7 天的提交，最多 100 个。

```bash
git log HEAD --since-as-filter='7 days ago' --max-count=100 --format=%H
```

按提交检查时，取各提交改动路径的并集，核对重命名后的路径和已删除文件的引用。
按目录或全仓检查时，从范围内的源码和现行文档入手。沿调用关系读取必要上下文。

## 选择值得做的改动

同时检查局部实现和文件职责，选择收益明确、可以独立验证的一批改动。
没有合适的候选时，可以零改动结束。

- 合并重复业务规则前，比较各调用方的默认值、失败分支和副作用。
- 简化过深的分支或无意义的转发层时，保留错误传播、重试和取消语义。
- 文件混合了不同职责时，根据调用方和依赖确定逻辑的归属。
  移动前核对构建目标、模块依赖和资源路径。
- 退役代码前，核对静态调用、动态注册、配置引用和旧数据兼容入口。
  用途仍无法确认时，保留代码并说明缺少哪项依据。

## 核对代码与文档

从候选代码找描述其行为的文档，也从候选文档反查实际入口。
优先核对用户会依赖的细节，例如命令参数、配置默认值、重试条件和资源路径。

只报告在同一版本、构建配置和功能开关下，能够由实现、配置或可复现结果证实的矛盾。
历史记录按其对应版本判断。

已有差异默认提示用户，需要确定预期行为时说明待决定的问题。
若本轮改动使文档过时，在授权范围内同步并复核。

## 验证与交付

按项目规则构建、测试和交付。根据改动验证受影响的入口，确认公开接口、旧数据读取、
错误处理、重试和恢复等可观察行为得到保留。

简述检查范围、改动收益和验证结果。仍待确认的重构或退役候选，说明原因。
即使本轮零改动，也应提示已证实的文档差异。给出文档和实现的位置，说明两者的差异、
对使用者的影响以及处理状态。
