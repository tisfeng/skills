# 代码维护

1. **确认授权和范围。** 先读宿主项目规则并检查工作树，保护已有改动。用户要求清理或重构时，在授权范围内执行。只要求检查、评估或方案时，仅做只读取证和报告，保持文件、Git 状态和外部服务原样。只读查看 Git 状态可用 `git --no-optional-locks status --short`。
   - 有指定提交范围、目录或全仓时，直接按指定范围取候选。
   - 未指定范围时，从当前 `HEAD` 可达的历史选最近 7 天的提交，最多 100 个，以先达到的边界为准。可用 `git log HEAD --since-as-filter='7 days ago' --max-count=100 --format=%H`。没有符合条件的提交时，可直接报告零改动。
2. **定位候选。** 提交范围取各提交改动路径的并集，核对重命名和删除后的当前路径。目录或全仓范围从指定位置的源码取候选。沿调用关系读必要的调用方、测试、配置和数据格式，修改遵守用户给出的范围。
3. **选择一批能独立验证的改动。** 同时看局部实现和文件组织，优先处理重复的业务规则、过深的分支、无意义的转发、职责混杂和文件归属。移动文件时核对构建目标、模块依赖和资源路径。退役代码前核对静态调用、动态注册、配置和兼容入口，证据不足的候选留待确认。没有明确收益或无法证明行为一致时，可以零改动结束。
4. **保持行为并验证。** 保留公开接口、旧数据兼容和其他可观察行为，尤其是错误分类、重试、取消、持久化和恢复语义。实际改动后按宿主项目要求运行适用的构建、测试和交付流程，覆盖受影响的入口、失败路径和兼容场景。报告实际检查范围、改动及收益、验证结果和仍待确认的候选。
