# 代码与文档维护

## 确定范围

先读项目规则，检查工作树并保护已有改动。用户要求清理代码或整理文档时，在授权范围内执行。
用户只要求检查、评估或方案时，仅读取和报告。

用户指定文件、目录、提交范围或全仓时，以指定范围为准。
否则，从当前 `HEAD` 可达的历史中选取最近 7 天的提交，最多 100 个。

```bash
git log HEAD --since-as-filter='7 days ago' --max-count=100 --format=%H
```

按提交检查时，取各提交改动路径的并集，核对重命名后的路径和已删除文件的引用。
按目录或全仓检查时，从范围内的源码和现行文档入手。沿调用关系读取必要上下文。

## 清理代码

同时检查局部实现和文件职责，选择收益明确、可以独立验证的一批改动。
没有合适的候选时，可以零改动结束。

- 合并重复业务规则前，比较各调用方的默认值、失败分支和副作用。
- 简化过深的分支或无意义的转发层时，保留错误传播、重试和取消语义。
- 文件混合了不同职责时，根据调用方和依赖确定逻辑的归属。
  移动前核对构建目标、模块依赖和资源路径。
- 退役代码前，核对静态调用、动态注册、配置引用和旧数据兼容入口。
  用途仍无法确认时，保留代码并说明缺少哪项依据。

## 整理 Markdown

先读 Markdown 源文和项目排版约定，找出过长的正文行、混在一段里的多个主题和层级难辨的列表。

- 沿用项目的行长约定。没有约定时，普通正文以每行 80–100 个源码字符为参考。汉字、英文字母、标点、空格和 Markdown 标记中的每个字符都计为一。
- 长段落按主题分段。能在参考上限内写完的句子或列表项保持一行。过长时，选靠近参考长度的句末或自然分句换行，避免续行只剩几个字。
- 保留表格行、代码块、行内代码、链接目标、列表续行缩进和有意的硬换行。单个长 URL 可以独占一行，多处长链接可使用引用式链接。
- 只整理排版时，保留原文措辞、事实和先后关系。核对正文、命令、链接和标题锚点，检查调整后的段落与列表是否按预期渲染。

## 核对代码与文档

从候选代码找描述其行为的文档，也从候选文档反查实际入口。
优先核对用户会依赖的细节，例如命令参数、配置默认值、重试条件和资源路径。

只报告在同一版本、构建配置和功能开关下，能够由实现、配置或可复现结果证实的矛盾。
历史记录按其对应版本判断。

已有差异默认提示用户，需要确定预期行为时说明待决定的问题。
若本轮改动使文档过时，在授权范围内同步并复核。

## 验证与交付

按项目规则验证和交付。纯排版改动检查 Markdown。代码改动验证受影响的入口，
确认公开接口、旧数据读取、错误处理、重试和恢复等可观察行为得到保留。

简述检查范围、改动收益和验证结果。仍待确认的重构或退役候选，说明原因。
即使本轮零改动，也应提示已证实的文档差异。给出文档和实现的位置，说明两者的差异、
对使用者的影响以及处理状态。
